Hi, I’m Soham. You asked whether a sixty-engineer fintech could replace a $250,000 internal-tool platform while adding ten more apps. I tested whether Devin could build a useful tool, change it, and reuse the foundation. My recommendation is to keep the existing Power Apps workflows and pilot Devin on one new, low-risk tool.

Power Apps gives you more than screens: connectors, managed data, permissions and release tooling. Building means taking ownership of those responsibilities. Ten more apps also don’t automatically mean ten more license fees. We need to establish how much of the existing contract is actually removable.

I’ll start with Playbooks. Create, Update, Variant and Health turn recurring work into instructions Devin can reuse. The repository carries setup and verification steps between sessions. Someone still needs to design that foundation, but later requests can describe the business change in ordinary language.

Here’s the build session and refunds dashboard. I open a request, enter a reason and approve it. The status and history persist together. A fresh session then added the over-forty-eight-hours filter, and another reused the foundation for Merchant Reviews. These tools have separate records and shared components. Their selectable personas are demo identities, and no money moves.

The automation connects a request to a Playbook, an execution identity and a usage limit. Our update run needed a manual launch and a publishing handoff. The health run completed its checks, but its delayed start overlapped a manual retry. I wouldn’t describe either as proven unattended maintenance.

I added a separate follow-up experiment to test integration and access boundaries. This Settlement Review app calls a simulated vendor over HTTP using server-to-server OAuth. Microsoft documents that Power Apps custom connectors don’t directly support this client-credentials grant. Power Platform could still do it through an intermediary. The advantage here is implementing the connection directly in our backend; the tradeoff is owning that code.

In this app, the server owns each user’s role and tenant. The viewer sees limited information and cannot approve, even by changing the API request. The operator can record a decision for their own tenant. Another tenant cannot fetch that record. The vendor credentials stay behind the backend. These are public demo accounts, not enterprise sign-in, and the vendor data is fictional.

Now look at the separate controls on Devin. The follow-up automation is configured for a specific repository and an approved command from my GitHub account. Tags help find the work; they don’t grant permission. The session ran under a read-only security profile and returned a patch for separate review and publication. This run was manually launched, so the external trigger filters remain unverified. We also distinguish configured restrictions from the checks we actually observed.

The financial case depends on ownership, not the first build time. Using illustrative assumptions of $250,000 per engineer, $20,000 annual running costs and $50,000 initial production work, a quarter of an additional engineer puts year one near $133,000; one engineer puts it at $320,000. That competes with the product roadmap.

I’d run a thirty-day pilot with a named owner. Measure turnaround, review and support hours; validate sign-in, audit, backups and releases; then compare the cost with removable license spend. If those numbers don’t work, keep Power Apps and use Devin for supporting integration and testing.
